# RoomCraft Shared Data Contract

This document defines the data structures shared between the frontend,
backend, database, and genetic algorithm.

Changes to this contract must be discussed and agreed upon by both
Person A and Person B before implementation.

---

## 1. Units and Coordinate System

- All room dimensions are measured in centimeters (cm).
- All furniture dimensions are measured in centimeters (cm).
- All positions are measured in centimeters (cm).
- Rotation is measured in degrees.
- For v1, allowed furniture rotations are:
  - 0°
  - 90°
  - 180°
  - 270°
- Coordinate origin `(0, 0)` is the top-left corner of the room.
- `x` increases from left to right.
- `y` increases from top to bottom.

---

## 2. FurnitureCatalog

Represents a furniture item available for placement.

### Structure

    FurnitureCatalog {
      id,
      name,
      width,
      depth,
      category,
      tags
    }

### Fields

| Field                | Type     | Description                              |
|----------------------|----------|------------------------------------------|
| `id`                 | string   | Unique furniture identifier              |
| `name`               | string   | Display name of the furniture            |
| `width`              | number   | Furniture width in centimeters           |
| `depth`              | number   | Furniture depth in centimeters            |
| `category`           | string   | Furniture category                       |
| `tags`               | string[] | Spatial and functional properties        |

### Supported Tags

The initial catalog may use tags such as:

- `light-preferring`
- `light-avoiding`
- `must-be-near-wall`

Additional tags may be introduced later if required by the algorithm.

### Example

    {
      "id": "double-bed",
      "name": "Double Bed",
      "width": 160,
      "depth": 200,
      "category": "bed",
      "tags": ["must-be-near-wall"]
    }

## 3. Room

Represents a room configured by the user.

### Structure

    Room {
      userId,
      width,
      height,
      doors,
      windows,
      furnitureSelection
    }

### Fields

| Field                | Type     | Description                              |
|----------------------|----------|------------------------------------------|
| `userId`             | string   | ID of the user who owns the room         |
| `width`              | number   | Room width in centimeters                |
| `height`             | number   | Room height in centimeters               |
| `doors`              | Door[]   | Doors present in the room                |
| `windows`            | Window[] | Windows present in the room              |
| `furnitureSelection` | string[] | IDs of selected furniture from catalog   |

---

### Structure

### Allowed Wall Values

    "bottom"
    "left"

      "wall": "top"

### 3.3 Furniture Selection

The room stores furniture selections using their catalog IDs.

    furnitureSelection: string[]

### Example

    {
      "furnitureSelection": [
        "double-bed",
        "wardrobe",
        "nightstand",
        "desk",
        "office-chair"
      ]
    }

The actual furniture dimensions and properties are resolved from
`furnitureCatalog.json` / the furniture catalog database.

## 4. GeneratedLayout

Represents a furniture arrangement generated by the layout algorithm.

### Structure

    GeneratedLayout {
      roomId,
      layout,
      scores,
      isParetoOptimal,
      createdAt
    }

### Fields

| Field             | Type         | Description                                      |
|-------------------|--------------|--------------------------------------------------|
| `roomId`          | string       | ID of the room for which layout was generated   |
| `layout`          | LayoutItem[] | Furniture positions and rotations                |
| `scores`          | ScoreVector  | Four objective-function scores                   |
| `isParetoOptimal` | boolean      | Whether layout belongs to Pareto front           |
| `createdAt`       | Date         | Time at which layout was generated               |

---

### 4.1 LayoutItem

Represents the position of one furniture item inside a generated layout.

### Structure

    LayoutItem {
      furnitureId,
      x,
      y,
      rotation
    }

### Fields

| Field         | Type   | Description                                             |
|---------------|--------|---------------------------------------------------------|
| `furnitureId` | string | ID referencing the furniture catalog                    |
| `x`           | number | X-coordinate of furniture placement in centimeters     |
| `y`           | number | Y-coordinate of furniture placement in centimeters     |
| `rotation`    | number | Rotation in degrees: 0, 90, 180, or 270                |

### Example

    {
      "furnitureId": "double-bed",
      "x": 120,
      "y": 180,
      "rotation": 90
    }

---

### 4.2 ScoreVector

Each generated layout receives four independent objective scores.

### Structure

    ScoreVector {
      trafficFlow,
      lightExposure,
      clearance,
      clustering
    }

### Fields

| Field           | Type   | Description                                                     |
|-----------------|--------|-----------------------------------------------------------------|
| `trafficFlow`   | number | Score representing quality of walking paths                    |
| `lightExposure` | number | Score representing furniture placement relative to windows    |
| `clearance`     | number | Score representing spacing and ergonomic constraints           |
| `clustering`    | number | Score representing proximity of functionally related furniture |

The four scores remain separate.

They must **not** be permanently combined into a single score because
Pareto-front selection requires independent objective values.

## 7. Genetic Algorithm Contract

The genetic algorithm operates on candidate layouts represented as
chromosomes.

### Chromosome Structure

    Chromosome = [
      {
        furnitureId,
        x,
        y,
        rotation
      }
    ]

Each chromosome represents one complete furniture arrangement.

For every candidate layout, the algorithm calculates the four objective
scores:

    [
      trafficFlow,
      lightExposure,
      clearance,
      clustering
    ]

The scores remain independent throughout optimization.

The algorithm eventually extracts the non-dominated layouts to form the
Pareto front.

## 8. API Data Contract

The frontend and backend communicate using the structures defined in
this document.

### 8.1 Create Room

    POST /rooms

### Request Body

    {
      "width": 500,
      "height": 400,
      "doors": [
        {
          "x": 250,
          "y": 0,
          "wall": "top"
        }
      ],
      "windows": [
        {
          "x": 400,
          "y": 0,
          "wall": "top"
        }
      ],
      "furnitureSelection": [
        "double-bed",
        "desk",
        "office-chair"
      ]
    }

The backend associates the room with the authenticated user.

---

### 8.2 Generate Layouts

    POST /rooms/:id/generate

The endpoint receives a room ID and generates candidate furniture
layouts.

The response will contain generated layouts following the
`GeneratedLayout` structure defined above.

---

### 8.3 Get Generated Layouts

    GET /rooms/:id/layouts

Returns generated layouts associated with the specified room.

---

## 9. Contract Rules

1. All dimensions and coordinates use centimeters.
2. The coordinate origin is the top-left corner of the room.
3. Rotation is limited to 0°, 90°, 180°, and 270° in v1.
4. Furniture is referenced by `furnitureId`.
5. Furniture properties come from the shared furniture catalog.
6. Room furniture selection contains catalog IDs, not duplicated furniture data.
7. Generated layouts contain placement information, not duplicated furniture dimensions.
8. Generated layouts contain four independent objective scores.
9. Pareto optimization operates on the separate objective scores.
10. Changes to this shared contract must be discussed and agreed upon by both
    Person A and Person B before implementation.
