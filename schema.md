# RoomCraft Shared Data Contract

This document defines the shared data structures between the frontend,
backend, database, and genetic algorithm.

Changes to this contract must be discussed and agreed upon by both
Person A and Person B before implementation.

---

## 1. Units and Coordinate System

- All room dimensions are measured in centimeters (cm).
- All furniture dimensions are measured in centimeters (cm).
- All positions are measured in centimeters (cm).
- Rotation is measured in degrees.
- Allowed furniture rotations for v1:
  - 0°
  - 90°
  - 180°
  - 270°
- Coordinate origin `(0, 0)` is the top-left corner of the room.
- `x` increases from left to right.
- `y` increases from top to bottom.

---

## 2. FurnitureCatalog

Represents a furniture item available for placement.

### Structure

    FurnitureCatalog {
      id,
      name,
      width,
      depth,
      category,
      tags
    }

### Fields

| Field | Type | Description |
|---|---|---|
| `id` | string | Unique furniture identifier |
| `name` | string | Display name of the furniture |
| `width` | number | Furniture width in centimeters |
| `depth` | number | Furniture depth in centimeters |
| `category` | string | Furniture category |
| `tags` | string[] | Spatial and functional properties |

### Supported Tags

The initial catalog may use tags such as:

- `light-preferring`
- `light-avoiding`
- `must-be-near-wall`

Additional tags may be introduced later if required by the algorithm.

### Example

    {
      "id": "double-bed",
      "name": "Double Bed",
      "width": 160,
      "depth": 200,
      "category": "bed",
      "tags": ["must-be-near-wall"]
    }

## 3. Room

Represents a room configured by the user.

### Structure

    Room {
      userId,
      width,
      height,
      doors,
      windows,
      furnitureSelection
    }

### Fields

| Field | Type | Description |
|---|---|---|
| `userId` | string | ID of the user who owns the room |
| `width` | number | Room width in centimeters |
| `height` | number | Room height in centimeters |
| `doors` | Door[] | Doors present in the room |
| `windows` | Window[] | Windows present in the room |
| `furnitureSelection` | string[] | IDs of selected furniture from the catalog |

### 3.3 Furniture Selection

The room stores furniture selections using their catalog IDs.

    furnitureSelection: string[]

### Example

    {
      "furnitureSelection": [
        "double-bed",
        "wardrobe",
        "nightstand",
        "desk",
        "office-chair"
      ]
    }

The actual furniture dimensions and properties are resolved from the
shared furniture catalog.

## 4. GeneratedLayout

Represents a furniture arrangement generated by the genetic algorithm.

### Structure

    GeneratedLayout {
      roomId,
      layout,
      scores,
      isParetoOptimal,
      createdAt
    }

### Fields

| Field | Type | Description |
|---|---|---|
| `roomId` | string | ID of the room for which the layout was generated |
| `layout` | LayoutItem[] | Furniture positions and rotations |
| `scores` | ScoreVector | Four objective-function scores |
| `isParetoOptimal` | boolean | Whether the layout belongs to the Pareto front |
| `createdAt` | Date | Time at which the layout was generated |

---

### 4.1 LayoutItem

Represents the position of one furniture item inside a generated layout.

### Structure

    LayoutItem {
      furnitureId,
      x,
      y,
      rotation
    }

### Fields

| Field | Type | Description |
|---|---|---|
| `furnitureId` | string | ID referencing the furniture catalog |
| `x` | number | X-coordinate of furniture placement in centimeters |
| `y` | number | Y-coordinate of furniture placement in centimeters |
| `rotation` | number | Rotation in degrees: 0, 90, 180, or 270 |

### Example

    {
      "furnitureId": "double-bed",
      "x": 120,
      "y": 180,
      "rotation": 90
    }

---

### 4.2 ScoreVector

Each generated layout receives four independent objective scores.

### Structure

    ScoreVector {
      trafficFlow,
      lightExposure,
      clearance,
      clustering
    }

### Fields

| Field | Type | Description |
|---|---|---|
| `trafficFlow` | number | Score representing the quality of walking paths |
| `lightExposure` | number | Score representing furniture placement relative to windows |
| `clearance` | number | Score representing spacing and ergonomic constraints |
| `clustering` | number | Score representing proximity of functionally related furniture |

The four scores must remain separate.

They must not be permanently combined into a single score because
Pareto-front selection requires independent objective values.

---

## 5. Genetic Algorithm Contract

The genetic algorithm operates on candidate layouts represented as
chromosomes.

### Chromosome Structure

    Chromosome = [
      {
        furnitureId,
        x,
        y,
        rotation
      }
    ]

Each chromosome represents one complete furniture arrangement.

For every candidate layout, the algorithm calculates the four objective
scores:

    [
      trafficFlow,
      lightExposure,
      clearance,
      clustering
    ]

The scores remain independent throughout optimization.

The algorithm eventually extracts the non-dominated layouts to form the
Pareto front.

## 8. Contract Rules

1. All room dimensions use centimeters.
2. All furniture dimensions use centimeters.
3. All positions and coordinates use centimeters.
4. Rotation uses degrees.
5. Allowed rotations in v1 are `0`, `90`, `180`, and `270`.
6. The coordinate origin `(0, 0)` is the top-left corner of the room.
7. `x` increases from left to right.
8. `y` increases from top to bottom.
9. Furniture is referenced using `furnitureId`.
10. Furniture properties are resolved from the shared furniture catalog.
11. `Room.furnitureSelection` contains furniture catalog IDs, not duplicated furniture data.
12. `GeneratedLayout.layout` contains furniture placement information.
13. `GeneratedLayout.layout` does not duplicate furniture dimensions.
14. Generated layouts contain four independent objective scores.
15. The objective scores must not be permanently blended into one score.
16. Pareto optimization operates on the separate objective scores.
17. `GeneratedLayout.roomId` identifies the room associated with the generated layout.
18. `isParetoOptimal` indicates whether the generated layout belongs to the Pareto front.
19. Changes to this shared contract must be discussed and agreed upon by both Person A and Person B before implementation.
